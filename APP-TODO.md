# Twiggli app (FlutterFlow): to-do

- **Update the Firebase SDKs (security patch, within 2–4 weeks).** Firebase warned on 03.11.26 ("[Act Now] Upgrade your Firebase SDKs for Firestore"): the eMudhra CA keys were compromised, and Flutter/iOS Firestore SDKs bake the old certificates into the app, so a forged certificate could let someone on the same network read or change app traffic (logins, profiles, bookings). Project twiggli-production is listed. The app (repo thejijoju/Twiggli, v1.0.33, last commit 19.02.26) still uses cloud_firestore 5.6.9, firebase_core 3.14.0, firebase_auth 5.6.0, firebase_storage 12.4.7, firebase_messaging 15.2.7, cloud_functions 5.5.2, firebase_crashlytics 4.3.7. Steps: raise all FlutterFire packages to the patched versions (several major versions, so some app code may need changes), rebuild and test, publish a new version (e.g. 1.0.34) to the App Store and Google Play, then ask users to update (forced update if possible). Needs Flutter + Xcode and store access, so not doable from a cloud session; Claude can prepare the branch with the package bumps and code fixes plus a build guide. Website and Cloud Functions are not affected (web SDK and server SDK). Guide: https://firebase.google.com/support/guides/compromised-emudhra-intermediate-ca (04.11.26)
- **Roll the Stripe live secret key and the Bunny Stream key.** The app's code holds both in plain text: the full Stripe secret key as the default `apiKey` in `firebase/functions/api_manager.js` (the Stripe API calls), and the Bunny key in `assets/environment_values/environment.json`, which ships inside the app. Roll both in their dashboards, then keep them only in Firebase Secret Manager and have the functions read them there. Rolling the Stripe key breaks the app's Stripe calls until FlutterFlow uses the new one. (30.10.26)
- **Know who signs in with Apple.** Sign in with Apple stays on: switching it off locks out everyone who signed up with it, and the App Store requires it next to Google login. "Hide My Email" users get a relay address (…@privaterelay.appleid.com) that still forwards mail. After any sign-in, ask for name plus phone number or a real email before someone can book. (29.10.26)
- **Tighten the Firestore rules.** Some collections (payments, transactions, Users, stripeaccounts) can be written by any signed-in user. Rules are in `firestore.rules`, published by hand in the Firebase console. (29.10.26)

- Hosts must say whether their studio is barrierefrei / wheelchair accessible (step-free entrance, space, accessible WC) and whether they come to the client: add the question to the host account and onboarding, and show the "Rollstuhlgerecht" tag (site/src/data/hostTags.ts) where it is a yes. Known 02.11.26: Celina yes (ground floor); Petite Jungle, Marija, Druckrausch no (they come on site); Angelo has an accessible room.
- **Show each date's cancellation policy to guests.** Hosts choose it when they create a date in their account (HostAccountPage: free up to 24 h / 7 days / 14 days before, no refunds, or since 04.11.26 "no refund, but can be moved to a later date", which is fave studio's rule). It is stored with the date but not shown anywhere yet: show it on the date row, in the booking form and in the guest's confirmation email once host-account dates go public; and with Stripe, "move" means no refund but a voucher or rebooking for a later date of the same host. (04.11.26)
- **Host account: show and edit every existing date and workshop from day one.** When a host opens their account, they must already see all their upcoming dates and the workshops they belong to, exactly as guests see them on twiggli.com, and be able to change or cancel them. Today the account (HostAccountPage) only lists dates the host created there (Firestore hostEvents) plus requests; it does not know the dates already public on the site. Those come from two places: the daily scrape of the host's own site/Konfetti/shop (site/src/data/live-workshops.json, scripts/update-workshops.mjs) and dates we entered by hand (site/src/data/hostDates.ts, e.g. Pigi's Saturdays, Jeannette, fave studio), with places booked through us in availability.ts. Plan: (1) on first login (or when Jirel approves the host), import those dates and the workshop texts, prices, places, photos and cancellation policy into the host's account as their own editable dates and workshops; (2) mark the host as "manages own dates" so the scraper and hostDates.ts stop overriding them (no double dates); (3) every change in the account goes live on the site and in the calendar, and guests who booked or wait for a changed or cancelled date are told; (4) workshops are the parent (title, description, photos, price, duration, group size, cancellation policy), dates hang under them, so a host edits a workshop once and adds dates to it. Visual design still open: Luma (event pages, guest list, simple date creation) and Airbnb (host calendar, listing editor, requests and messages) as references. (Jirel, 04.11.26)
- **Host request emails like Airbnb's: one click, an amount, a deadline, reminders.** Today the host gets a personal email and has to write to the guest themselves; there is no deadline, no amount, no reminder, and we often never learn the outcome (many "Unbekannt" rows in the Schätzung tab; Jana/Loam and Qian went quiet). Airbnb's host email ("Reminder: Reservation Request…") converts better because the host can say yes in one click and is chased until they do. Plan, possible before host accounts: (1) buttons in the host email "Accept", "Suggest another date", "Decline", each opening that request in the host's own account (twiggli.com/host/account/requests/<id>, HostAccountPage), signed in straight from the link via the existing email-link sign-in; the account marks the request in Firestore and emails the guest automatically, puts an accepted date under Dates, sends suggested dates to the guest for a one-click pick, and asks a decline reason the guest never sees. Mock-up: https://claude.ai/artifact/KDwZCWnjtZikSecM9EHxT7; (2) show the booking value and the host's payout after commission; (3) a 48 h deadline: reminder to the host after 24 h, after 48 h a note to Jirel and an email to the guest with alternative hosts on the same date; (4) keep Jirel's personal line at the top. Bonus: the request status feeds the Schätzung tab and the daily check automatically. Later the same flow moves into the host account. (Jirel, 05.11.26)
- **Build the full host dashboard (needed before the one-click request emails work).** The request buttons only make sense if they land in a real host account. HostAccountPage (twiggli.com/host/account, email-link and Google sign-in) today lists only dates the host created there plus requests. It needs four tabs: (1) **Requests**: every request with status (new, accepted, date suggested, declined, expired), the 48 h countdown, Accept / Suggest up to 3 dates / Decline with a private reason, and the guest's reply to suggested dates; one page per request at /host/account/requests/<id>, opened signed in straight from the email link; (2) **Dates**: all upcoming dates, including the ones imported from the site (see the "show and edit every existing date" item), places booked/left, waiting list, change or cancel with guests told automatically, and pausing new requests while away; (3) **Workshops**: title, text, photos, price, duration, group size, cancellation policy, with dates hanging under them; (4) **Payouts**: booking value, 15% commission (or "first booking free"), payout per booking and per month, later through Stripe Connect. Every action writes to Firestore, updates the site and the Schätzung tab, and emails the guest. Mock-up of the request pages: https://claude.ai/artifact/KDwZCWnjtZikSecM9EHxT7; sample host email: Gmail draft "[SAMPLE] New request: team event for 11". (Jirel, 05.11.26)
